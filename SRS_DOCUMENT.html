1. Introduction & Project Scope

Software maintenance represents over 60% to 70% of the total software lifecycle expenditure. The DevCore Bug Tracker is a full-lifecycle defect tracking and quantitative metrics evaluation system. It is engineered to fulfill all four lab syllabus outcomes:

  1. Analyze Maintenance Requirements: IEEE classification into Corrective, Adaptive, Perfective, and Preventive maintenance.
  2. Bug Life Cycle Workflows: Formal state machine governing state transitions (New → Assigned → In Progress → Resolved → Under Retest → Closed / Reopened).
  3. Issue Tracking & Traceability: Capture detailed steps, environment, priority, severity, and audit history.
  4. Process Improvement Metrics: Real-time evaluation of DSI, MTTR, Defect Density (KLOC), and Reopen Rate.

2. Stakeholder Roles (Traditional & Agile / Scrum Context)

In software engineering, role allocation depends on whether the team uses a standard maintenance model or an Agile/Scrum framework:

Role Day-to-Day Responsibilities in DevCore Agile / Scrum Role Equivalent
QA / Test Engineer Finds and logs bugs with reproduction steps; verifies fixes during retest; closes or reopens tickets. Development Team Member (Tester)
Developer / Software Engineer Investigates root cause, develops code patch, conducts unit testing, and marks ticket as Resolved. Development Team Member (Coder)
Project Manager (PM) Triages incoming bugs, sets Priority/Severity, assigns developers, and monitors release quality. Product Owner (PO) (Prioritizes bug backlog against feature user stories)
Scrum Master (Optional Agile Facilitator) Does not fix bugs directly. Uses the Metrics Dashboard (DSI, MTTR, Reopen Rate) during Sprint Retrospectives to eliminate delivery blockers and optimize sprint velocity. Scrum Master

3. Functional Requirements

  • FR-1 (Maintenance Categorization): Every ticket must be classified as Corrective (fault fix), Adaptive (environment change), Perfective (enhancement), or Preventive (refactoring).
  • FR-2 (Finite State Machine): Defect status transitions must follow strict protocol: NEW → ASSIGNED → IN PROGRESS → RESOLVED → UNDER RETEST → CLOSED. If retest fails, it must transition to REOPENED.
  • FR-3 (Audit Trail & Traceability): Any state modification automatically logs an immutable record with actor name, timestamp, previous status, and justification reason.
  • FR-4 (Software Process Metrics):
    • Defect Severity Index (DSI): Weighted severity score: [(4 × Critical) + (3 × High) + (2 × Medium) + (1 × Low)] / Total Defects.
    • Mean Time to Resolution (MTTR): Average duration in hours/days between defect logging and resolution.
    • Defect Density: Total defects divided by module size in KLOC (Thousands of Lines of Code).
    • Defect Reopen Rate: Percentage of resolved tickets that failed verification: (Reopened Count / Resolved Count) × 100.
